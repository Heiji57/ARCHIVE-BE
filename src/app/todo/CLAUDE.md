# Todo 모듈 컨벤션

이 디렉토리(`src/app/todo/`)에서 작업할 때 적용되는 컨벤션. 루트 `CLAUDE.md`의 Key Conventions에서 이관됨.

- **Todo 시간 저장 정책**: `todos.start_time` / `todos.end_time` 은 UTC `TIMESTAMPTZ` 로 저장. 사용자 로컬 시각 복원을 위해 생성 시점 IANA timezone 을 `todos.timezone`(`VARCHAR(50)`) 에 함께 저장 (스냅샷). FE 는 로컬 시각을 UTC 로 변환해 전송하고, 응답의 `timezone` 으로 역변환. `start_time` 또는 `end_time` 이 non-null 이면 `timezone` 필수 (422). IANA 검증은 `shared/domain/utils/timezone.py`의 `validate_timezone` 사용.
- **Todo 날짜 이동 정책**: 시간 있는 todo 는 `start_time`(없으면 `end_time`)의 로컬 날짜(`todos.timezone` 기준) = `date_key` 를 유지한다. `start_time` 이 날짜까지 담은 UTC 시각이라, `date_key` 만 바꾸면 둘이 모순되고 Google Calendar push(시간 이벤트는 `start_time`/`end_time` 만 사용)가 옛 날짜에 남는다. 그래서 `Todo.move_to()` 가 로컬 벽시계 시각과 start~end 일수를 유지한 채 start/end 를 새 날짜로 평행이동한다(FE 는 `dateKey` 만 보내도 된다). 같은 PATCH 의 명시 `start_time`/`end_time` 이 우선하며, `_apply_patch` 는 `timezone` 을 `date_key` 보다 먼저 적용한다. 반대 방향도 같다 — `date_key` 없이 `start_time`/`end_time`/`timezone` 만 바뀌어 로컬 날짜가 넘어가면 `Todo.align_date_to_time()` 이 `date_key` 를 새 로컬 날짜로 맞춘다. 단 시리즈 base 는 제외(`date_key` = 시리즈 시작일이라 옮기면 모든 슬롯 계산이 바뀜).
- **반복 회차 GCal push 정책**: 예외 row(`series_id` 있음)의 push 여부는 예외 row 자신의 `calendar_push_status` 가 아니라 **master 의 연동 상태**를 따른다 — master 가 push 됨(`calendar_push_status` 있음, `push_intent != 'delete'`, `google_event_id` 있음)이면 예외 row 실체화/수정 시 `mark_for_push` 하고 `master_google_event_id` 스냅샷을 master 현재 gid 로 갱신한다. 워커는 이를 GCal instance PATCH(`{master_gid}_{originalStartTime UTC}`, 종일은 `{master_gid}_{YYYYMMDD}`)로 반영한다. master 가 아직 push 전(gid 없음)이면 instance ID 를 만들 수 없어 push 하지 않는다.
- **Todo due_date_key 정책**: `todos.due_date_key` (`VARCHAR(10)`, nullable) — 선택적 마감일(포함, YYYY-MM-DD). `due_date_key >= date_key` 제약 (422). POST: Pydantic model_validator에서 검증. PATCH: `omit=unchanged`, `null=clear`, `string=set` 패턴(UNSET sentinel). Pydantic 레벨에서 `date_key`가 같은 요청에 포함된 경우만 체크, 나머지는 `UpdateTodoUseCase._apply_patch`에서 `RequestValidationError` 발생. 반복 Todo exception row(`_materialize_and_update`) 및 following 분리(`_update_following`) 시 source/master의 `due_date_key` 상속.
- **`GET /todos/stats?range=all`**: 전체 기간 = `2000-01-01 ~ 오늘`. 상한을 `today` 로 두는 것은 "이미 쌓인" 개수라는 의미에 맞을 뿐 아니라 **안전장치**다 — `date.max` 로 두면 종료일 없는 반복 Todo 마다 `generate_slots_from` 가상 슬롯 루프가 서기 9999년까지 수백만 번 돌아 요청이 멈춘다. `today/week/month` 동작은 불변.
- **반복 규칙(RecurrenceRule) 정책**: unit = `day|week|month|year`, 의미는 RFC 5545 RRULE 과 같다 — 시작일(base `date_key` = DTSTART)은 규칙과 맞지 않아도 항상 첫 회차. `week` 는 `weekdays`(0=월…6=일, null=시작일 요일, 주 시작=월요일), `month` 는 `month_week`(1~4, -1=마지막; 필수) 번째 시작일-요일, `year` 는 시작일 월/일(2/29 는 윤년만). 가상 인스턴스 슬롯(`generate_slots_from`)과 GCal RRULE(`rule_to_rrule`)은 같은 `domain/utils/recurrence.py` 에서 같은 날짜 집합을 만들어야 한다(중복/누락 일정 방지) — 한쪽을 바꾸면 다른 쪽과 `test/test_recurrence_slots.py` 도 함께. 규칙을 복사(following 분리·삭제 시 until 단축)할 땐 필드를 하나씩 옮기지 말고 `dataclasses.replace(rule, until=…)` 로 나머지 필드를 보존한다. 가상 인스턴스는 base 판별(`is_series_base`)을 깨지 않도록 `recurrence_rule=None` 을 유지하고, 시리즈 규칙은 비영속 `Todo.series_rule` → 응답 `series_rule` 로만 노출한다. 신규 필드는 JSONB 에 값이 있을 때만 저장하므로 기존 day/week 데이터는 마이그레이션 없이 그대로 동작한다. **시리즈 base 불변식**: 시간 있는 base 는 `start_time` 의 로컬 날짜 == `date_key` 여야 한다 — 일반 todo 는 시간이 자정을 넘기면 `align_date_to_time()` 으로 date_key 를 옮기지만, base 는 date_key(시작일)를 옮길 수 없으므로 반대로 `anchor_time_to_date()` 로 시간을 date_key 에 맞춘다(생성·base 수정·following 분리의 새 base). 어긋나면 Google DTSTART 와 서버 슬롯 기준이 달라져 BYDAY RRULE 이 하루 밀린다.
